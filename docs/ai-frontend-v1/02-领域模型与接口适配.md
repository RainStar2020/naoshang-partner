# 领域模型与接口适配

内容配置以2026-10-22新增的07-后台富文本内容约定.md为准：等级权益/素材模板正文默认空，不写死示例文案、图片。

这些DTO/状态是前端约定建议，尚未冻结为正式后端契约。AI可用于Mock与适配器，不得声明已上线。

## 1. 不可合并的身份

Account=登录主体；Member=孩子；MemberEntitlement=学习权益；PartnerProfile=合伙等级；AnnualPartnerEntitlement=年度权益；AgencyAssignment=具体区域代理委任；StoreMembership=具体门店经营身份；CoStoreContract=合店合同；CoachProfile=健脑官任职。

建议Context：id、accountId、mode、memberId?、assignmentId?、storeId?、contractId?、capabilities[]、validUntil?。不要求每个mode同时有全部字段。选择器只能从bootstrap/合法候选列表切换，不能任意构造id获得权限。前端能力判断只决定展示，后端必须校验每次请求及私有媒体访问。

## 2. 前端内部DTO建议

内部Session沿用{token,user}兼容旧代码；新增expiresAt?、contexts?时避免破坏getSession。服务端accessToken或其他字段由适配器转换，页面不兼容多套命名。

ListResult：{items:[],nextCursor:null,hasMore:false}；ApiError：{kind,code,message,fieldErrors?,requestId?,retryable?}；Quote：{id,items,discounts,payableAmount,currency,expiresAt,ruleVersion}；允许动作：{code,enabled,disabledReason?}。未知字段保留在adapter边界，不散落模板。

金额内部统一整数分，格式化函数只负责展示。除输入字符串→分的确定性解析外，前端不承担采购价、分润、折扣叠加、手续费等规则计算。比例若以basis points记录，10000=100%，不可将15误当15%或15倍。零金额合法；null表示未知，不用value||fallback吞掉0。

日期内部统一毫秒或带时区ISO，适配器只转换一次，拒绝非法值。serverTime用于时钟偏差；显示和结算时区由业务确认。设计图2022年时间不用于正式判断。

## 3. 当前代码与提案的兼容差异

- 当前登录/注册存储返回token；上一版API提案写accessToken。先归一化为内部token，待后端确认后更新适配器。
- 当前H5微信authorize读取result.url；提案写authorizeUrl。联调前明确真实字段，不在页面中写url||authorizeUrl来掩盖契约未知。
- 当前注册发送wechatTicket；提案称registrationTicket。票据语义需要统一且一次性；只在service出入站转换，不向两个字段同时盲发。
- 当前短信调用只有phone/purpose，提案增加challengeId；若后端采用challenge，则useSms/auth需协同传递，不能只改页面。
- 当前/member/levels、/partners、/products为演示服务预留路径；学习新接口/members/{memberId}/levels改变了权限上下文和结构，需适配或显式迁移。
- 当前request直接resolve res.data；提案统一{code,data,message,requestId,serverTime}封装。只在request/adapter层解包，避免登录保存了整个envelope。
- 当前Mock短信123456、5分钟、60秒，重置票据5分钟、微信票据10分钟、邀请码缓存7天都是现有演示行为，真实有效期以服务端为准。

以上差异必须在接口联调记录中逐条解决；本包没有替后端选定最终字段。

## 4. 结算与订单

Product.categoryId控制目录；fulfillmentType控制履约。Mock建议PHYSICAL、ACTIVATION_CODE、OFFLINE_SERVICE、COLUMN_ACCESS等明确编码，商品分类到履约映射由服务端确认，不将名称匹配作为逻辑。

CheckoutDraft保存items(skuId,quantity)、storeId、memberId?、addressId?、couponId?、remark、quoteId?。任何计价/受益对象变化清空旧quote，重新询价。未选必填项可展示草稿，但创建订单前必须满足requiredFields。

Order.businessStatus建议PENDING_PAYMENT/CANCELLED/PAID/COMPLETED；fulfillmentStatus独立记录。UI“待发货/待收货”映射以最终契约为准，未知状态显示中性文案并禁用状态变更，不能默认completed。按钮来自allowedActions，后端仍二次校验。

支付链：quote→创建订单→渠道列表→payment attempt→平台适配→查询后台。平台回调成功只能触发查询；失败、取消、处理中、超时各自显示。控制有限轮询与页面卸载，未知结果不能直接允许重新创建另一笔订单。支付通知验签是后端职责，前端不得模拟线上入账。

## 5. 名额、收益与审批

QuotaBatch至少id/type/grantedAt/expiresAt/total/used/remaining；余额及批次扣减由后端决定，不能以界面递减替代交易。升级/划拨使用quote+idempotencyKey+version，操作后刷新余额、成员等级和流水。

IncomeEntry至少sourceOrder、beneficiaryContext、baseAmount、rateBps、amount、ruleVersion；allocationStatus、settlementStatus、withdrawalStatus分别表达。巡查inspection和销售sales使用不同kind，确认页必须显示实际受益人。

Application、Order、Contract、Entitlement分别记录审核、支付、合作、开通状态。申请已付款不等于已批准，批准不等于合同已生效。任何审批顺序未知时，真实动作按Q清单保留待定，Mock单独标演示路径。

## 6. 请求端规则

建议远程请求流程：配置校验→鉴权header→发起请求→HTTP/网络分类→响应envelope解析→DTO适配→返回页面。401统一失效会话且避免多个并发弹窗；403显示无权限，不能偷偷换其他身份数据。409/版本冲突先刷新，422按字段显示，429使用服务端retryAfter；这些HTTP映射待实际后端确认。

幂等key按一次业务意图生成，重试复用，改参数后新建。对不确定结果可查询已有操作/订单再决定下一步；不要全局给POST自动重试。API清单里的idempotencyKey在body还是header需统一确认。

上传先申请intent→按签名配置上传→complete→等待处理ready→提交业务引用。实际MIME/大小/归属由后端检查；前端也做即时校验。未完成文件不作为发布成功，私有媒体URL过期可重新申请。
