3. 升级支付：§18.3 已明确一张支付单，支付成功后扣名额并授级。服务费样例仍与正文冲突，见下。
4. 上传：§18.4 已明确 fileId=assetId、先上传字节再 completions、仅 READY 可用。真实上传服务和签名方法仍需现场联调。
5. 权益三态：§18.5 已明确 never_paid 计算但隐藏；expired 停算且允许导出；active 正常。bootstrap.gate 与顶层 locked 都需支持。
6. 收益多态：§18.6 已提供 14 类 detailFields 与字典端点；但同文档旧章节的枚举、占位符仍不一致。
7. 晋升领取：§18.7 已补 GET/POST /partner/promotion-claims；POST 示例只有响应，完整请求字段尚未列明。
8. 核销/幂等：§18.8 已补本店授权、已付才可核销、5 次失败锁定、参数不同返回 409。统一幂等表出现了不同命名路径，尚需确认是否别名。

结论：八项都已得到文字答复；并非八项均已成为无歧义、可直接上线的契约。

## 仍需后端确认，可直接转发

### 1. 金额逐字段单位未闭合（阻塞全局切换真实接口）

§0 写所有金额为元；§6.1 又明确商品展示 standardAmount/memberPrices/rolePrices/skus.amount 是分，而 prices 是元。该展示特例可以接受，但还需提供 checkout、order、coupon、withdrawal、metrics 各字段的明确单位。旧页面按分显示且提现输入乘 100，不能依据“全部元”粗暴迁移。

请补充：`goodsAmount/discountAmount/payableAmount/unitAmount`、订单项、优惠券折扣和门槛、专栏列表 price、支付 amount 的逐字段单位；最好响应增加 moneyUnit/currency 或 OpenAPI 字段注释。

### 2. 下单默认直接 paid（需明确生产行为）

§6.5 说明不传 payLater 就直接 paid。这与生产 live 必须渠道回调成功才认支付之间存在明显冲突。前端新建单应明确 payLater:true；后端还需说明 live 是否禁止免支付建单、是否有权限约束，以及返回的 paid/PENDING_PAYMENT 等状态是否统一大小写。

### 3. 门店分润归属仍待确认

§6.3 明示 storeId 仅记录、不参与分润，且门店归属口径待定。用户在结算页选门店与实际收益归属可能不同。必须明确最终以买家 regionCode、deliveryStore、storeId 还是其他字段确定，不能由前端推断。

### 4. 报价时间/提交字段/权益报价映射存在冲突

§18.1 说全部报价为 ISO expiresAt，§2.3/§4.2 仍是毫秒。客户端已有兼容解析，但请提供准确 schema。

§18.1 说“请求里带 quoteId 即可”，§6.5/§2.4 仍列 productKey/quantity/targetLevel。请给出每个提交端点的最小必填请求，并明确参数变化应重新报价；不能把“失败后可重试原报价”理解为可更换报价组合。

权益表把 `/partner/entitlement-quotes` 映射到 `/me/entitlement-orders`，而旧版该报价是年度合伙权益（1980），`/me` 是 200 元收益权益。请分别给出两种业务的 scene、报价/提交路径、amount，避免串用。

### 5. inspection/inspect 与业务类型 key 仍矛盾

§4 声明 inspection/sales、inspect 废弃；§18.6 仍写 inspect。兼容读取可以做，但客户端写哪个、字典实际返回哪个请统一。

§3.4 的 costore/global/founding 与 §18.6 的 costore_fee/global_bonus/founder_bonus 不同。请确认旧 key 是否别名、列表和详情是否返回同一套。新类型以 §18.6 为准；没有据此覆盖现有收益账。

### 6. 升级服务费样例不一致

§2 写活动名额每个服务费 2000，§18.3 的 breakdown.serviceFee 却为 300 且未说明名额组合。请解释是新规则、可配置还是样例错误。

### 7. 鉴权结构与路径别名未完整补齐

bootstrap 仍为简化示例，缺 capabilities、代理 assignmentId/agencyType、合店 contractId/storeId 和家庭 contexts。module 从 wholesale 改 partner，但未说明权限字符串是否也改。保留严格权限校验，不从标签伪造能力。

§18.8 幂等清单的 `/coaches`、`/training/feedback`、`/store-transfers`、`/material-renders` 与主文的资源路径不一致。请确认是别名还是笔误。本次未生成这些可疑入口。

### 8. 收益详情模板与门店核销约定仍不充分

detailFormat 用 `{商品类型}/{金额}` 等中文占位符，detailFields 用 productKind/paid；“按顺序回填”无法消除重复占位符及多种模板歧义。建议直接返回可渲染 detailText，或模板统一 `{productKind}/{paid}`。

核销表写 contextId 为“门店身份”，但没有给出具体身份结构；重复核销统一拒绝，首次成功响应丢失时前端如何查询确认也没说明。请提供核销响应、错误示例、读回核销状态的完整流程。

### 9. 支付与上传的真实外部服务仍需验证

payParams.invoke 尚无 H5 微信 JSAPI/跳转、小程序、支付宝、银行卡各平台的完整字段/取消/失败范例；上传地址示例仍为 example.com，并同时写 PUT/POST，而 mode 为 multipart。前端保留按签名 multipart POST，不猜对象存储方法。请提供可用联调环境、签名方法、上传完成响应及私有资源访问约定。
